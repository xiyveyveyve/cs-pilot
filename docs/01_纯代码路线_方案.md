## 一、调研结论（2026-11-10 实测）

### 1.1 前序路线盘点

| 路线 | 机制 | 卡点 | 结论 |
|---|---|---|---|
| 自研上位机 `CSDirect` | 直接手搓串口帧 | 需真机逐条验证；设备参数下发方式未明 | 可作协议参照，不作为主路线 |
| 寄生式 GUI（UIA） | 点菜单 + 填控件 + 点「停止」 | 4 实例并存时菜单焦点失效；48h 后 UI 状态漂移 | **不是纯代码，本路线要摆脱它** |
| 进程内装配（testbed） | PowerShell 反射加载 .NET 程序集 | 只有 PowerShell 脚本，无正式宿主；未做文件落盘 | **本路线的基础，要升级成独立宿主** |
| 纯代码测试床 E2E | 无头装配 SendMethodBytes → sim → 收包入库 | 未验证文件落盘；无独立可执行体 | **本路线的起点** |

### 1.2 本轮新查明的关键事实（csc 直编 C#，64 位进程内加载成功）

**（A）不依赖 PowerShell 也能装起来。** `C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe`
直接编译 C# 宿主，进程内 `Assembly.LoadFrom` 加载 9 个 CS6 程序集，`BaseContext` 实例化成功
（`PointCount=0`）。**不再需要 PowerShell + Add-Type 的反射长脚本**，宿主可以是一个正式的 exe。

**（B）`IConnect` 有两个实现，网口是 `SockectConnect`。**

```
CSStudio6.Connect.Com.SerialConnect   Open(string comName) / Open(string, int baud)
                                      OnPackReceive / OnPackLog / OnRemoteMsg
                                      CheckPackReceiveThread()
CSStudio6.Connect.Com.SockectConnect  同上（网口：Open("IP:PORT")）
```
→ 纯代码路径可以**直接选串口或网口**，不必经过软件 UI 的「通讯设置」。

**（C）★ 找到了文件落盘的代码入口。** `BaseContext` 暴露：

```
BeginStartWriteFile(bool isRestore)      开始写盘
BeginStartWriteFileNext()                续写下一段
WriteContext()                           写当前上下文头
WriteDataNow()                           把缓存数据刷盘
WriteCycle(int cycleCount, bool bDelay)  阶梯波周期写
EndWriteFile()                           收尾
BeginStartEisWriteFile(string, Experiment) / EndEisWriteFile() / WriteContextEIS(ZDataItem)
CalculateCD(int nIndex)                  算电流密度（软件自己算，不用我们复算）
```

→ **产物不需要 CS Studio 的 GUI 参与**，可以直接由宿主生成 `.cor`/`.txt`。
这是本轮最大的可行性突破：前序 testbed 只验证了「内存入库」，没验证「落盘」。

**（D）数据面完整可用（`IDataItem`，23 组）**

```
Add(ulong nIndex, double time, double volte, double current, double charge)   落数据
AddEisData(ulong, ZDataItem)                          EIS 落数据
TimeValues / VolteValues / CurrentValues / ChargeValues / Indexs / EisDatas
OrigE / OrigI（原始值）  DataLock（官方锁，读必须 lock）
```

**（E）`ExpComSendClass` 是完整控制面（40 个方法）**，本路线需要的只有 8 个：

```
SendMethodBytes(IBaseParams)     下发方法参数
SysStart(bool isClearData)       启动
SysStop()                        停止
SysReverse() / ACReverse()       反向
StartSample()                    采样标志
GetOcpValue(ref double)          ★ 直接问设备要 OCP 值（不用自己从数据流里算）
GetOcpValue2(ref double, ref double)  OCP + 电流
GetUID() / GetPstType() / GetSerialNumber() / GetRomVersion()
```

**（F）参数类是 public 未混淆、可反射可直调（已核 4 个实验类全属性表）**

```
OcpParams        TestTime / TestTimeUnit / UseStop / StopVoltBoundType / StopVolt / DeltaVolt
PotDynamicParams InitE / MidEOne / MidETwo / FinalE / ScanRate / *VsOcp / StopCurrent*
PotSquareParams  Initial_E / Step1..10 / Final_E / InitialTime / Time1..10 / FinalTime / Times
EISVSfrqParams   Init_Fre / Final_Fre / SineAmp / SineBias / Integral_Time / TenTwice / VsOcp
公共基类 BaseParams：FileName / FilePath / OcpValue / IsStop / IsStopEvent / Frq / SampleFrq / DevParam ...
```

**（G）Experiment 枚举实值（CS6，按名解析不要写死数字）**

```
ID_OCP=1   ID_PotDynamic=5   ID_EISVSFRQ=32   ID_AnyPotStatic=63
```

**（H）CS5 是另一套接口**（`CorrTest.CorrCom.SockectCom` / `CSTSockect`），
帧族 `AA+cmd+13B+SUM` 完全不同；`BaseContext` 无 `DataItem`，走 `ActiveExpClass`。
**本路线第一阶段只做 CS6**（CS350M），CS5 留作第二阶段。

## 二、方案设计

### 2.1 总体架构（三进程，纯代码，无 GUI）

```
┌──────────────────────────────────────────────────────┐
│ pilot.py  （Python 编排器）                            │
│  · 起模拟器 / 起宿主 / 读宿主 JSON 事件流               │
│  · 多机并行（一台一个 sim + 一个宿主，端口/串口独立）     │
│  · 判稳/判停策略在这里可插拔、可回归测试                 │
└───────────────┬──────────────────────┬───────────────┘
                │ 拉起来                │ 事件流(JSONL)
    ┌───────────▼──────────┐   ┌───────▼──────────────────┐
    │ sim (虚拟设备)        │   │ cspilot_host.exe（C#）    │
    │ 串口 CNCB0 / TCP 31001│◄──┤  · 加载 CS6 程序集（只读） │
    │ 可按回放文件推流       │   │  · IConnect → BaseContext │
    └──────────────────────┘   │  · ExpComSendClass 启停   │
                               │  · IDataItem 收数          │
                               │  · BeginStartWriteFile 落盘│
                               └───────────────────────────┘
```

**为什么宿主必须是 C# 而不是 PowerShell**：前序 testbed 用 `Add-Type` + 反射写了一个 400 行
PowerShell，每加一个实验要改字符串、错误定位极差、无法单元测试。C# 宿主可以直接
`using` 类型（编译期就报错）、可以写正常的方法和状态机、可以被 pytest 当作黑盒进程测。

**为什么编排器用 Python**：判稳算法、策略配置、报告生成在 Python 侧迭代最快，
且能直接复用前序已验证的 `OcpStabilizer` 思路（真实数据标定过：峰值峰峰值 + 斜率双约束）。

### 2.2 宿主进程协议（host ↔ pilot）

stdin 收一行 JSON 作业，stdout 每行一个 JSON 事件（JSONL），退出码 0/1。

```jsonc
// 输入（argv[1] 是作业文件路径）
{
  "mode": "serial" | "tcp",
  "endpoint": "COM90" | "127.0.0.1:31001",
  "out_dir": "C:\\...\\data\\run1",
  "experiments": [
    {"kind":"ocp",   "params":{"TestTime":100,"TestTimeUnit":1},
     "stop":{"type":"stabilize","slope_mv_per_min":5,"hold_sec":30,"window_sec":20,
             "max_sec":300}},
    {"kind":"tafel", "params":{"InitE":-0.3,"FinalE":0.8,"ScanRate":25,"ScanRateUnit":0},
     "stop":{"type":"current_density","limit":1.0,"confirm_n":2,"max_sec":900}},
    {"kind":"step",  "params":{"Initial_E":-0.2,"Step1":0.0,"Time1":10,"Times":3},
     "stop":{"type":"max_sec","sec":120}}
  ]
}
```

```jsonc
// 输出事件
{"t":0.02,"ev":"host","msg":"asms loaded"}
{"t":0.10,"ev":"connect","ok":true,"endpoint":"COM90"}
{"t":0.15,"ev":"sn","sn":"CS350M24030650","pst":"CS350M"}
{"t":0.20,"ev":"exp_start","kind":"ocp","file":"...\\ocp.cor"}
{"t":1.30,"ev":"point","kind":"ocp","n":12,"time":1.3,"E":-0.1412,"I":null}
{"t":52.6,"ev":"exp_stop","kind":"ocp","reason":"stabilized","dwell_t":52.6,"E":-0.0925}
{"t":52.7,"ev":"file","kind":"ocp","path":"...","bytes":35005}
{"t":52.8,"ev":"done","ok":true}
```

### 2.3 实验状态机（宿主内）

```
IDLE → CONNECT → PROBE(型号/SN) → for each exp: PARAMS → START → SAMPLE ⇄ EVAL → STOP → FLUSH → IDLE' → DONE
```

- **SAMPLE**：以 100ms 周期读 `ctx.PointCount`（内存读，不 tail 日志），差量取 `IDataItem` 新点
- **EVAL**：`StopPolicy` 接口，四种实现：`TimeLimit` / `Stabilize` / `CurrentDensity` / `MaxSeconds`
- **STOP**：`send.SysStop()` → 轮询 `!ctx.IsBusy` 或 `ExpMethodState != SysRuning`（超时兜底）
- **FLUSH**：`ctx.EndWriteFile()` → 校验文件大小/行数

### 2.4 落盘策略（两路都做，互为校验）

1. **软件自己的写盘**：`ctx.BeginStartWriteFile(false)` + 数据流中 `ctx.WriteDataNow()`
   → 得到原生 `.cor`（含 `CORRW ASCII` 头 + `ExpParmas=` 串）
2. **我们自己的写盘**：宿主在 STOP 后把 `IDataItem` 五集合导出成
   `CSStudioFile,<ExpType>,<base64(gzip(头))>` + 三列数据（格式已在 00 §5.4 逐字节复刻过）

两路对比 = 免费的验收：若 `.cor` 大小与行数与自写 txt 点数一致，说明收数无缺帧。

### 2.5 模拟器（复用 + 自建薄封装）

- 直接**只读复制**前序 `testbed/simdevice.py` 到 `code/sim/simdevice.py`（不改一行，
  保证与前序 57 项自测的协议行为一致）
- 本目录另写 `sim_launch.py`：按机器配置起 sim（串口或 TCP、回放文件、端口分配）
- **不用真机、不用 COM16/COM10/COM6**，全部走 com0com 或 TCP 高位端口

### 2.6 与前序方案的差异（为什么这是"新东西"而非重复）

| 维度 | 前序 testbed | 本方案 |
|---|---|---|
| 宿主形态 | PowerShell 脚本（不可测） | C# exe（可被 pytest 黑盒驱动） |
| 落盘 | ❌ 未验证 | ✅ 原生 `.cor` + 自写 txt 双路 |
| 数据出口 | console 文本抓取 | JSONL 事件流（机读） |
| 策略 | 硬编码在脚本里 | `StopPolicy` 可插拔 + Python 侧回归测试 |
| 多机 | 靠 fleet + GUI 焦点互斥 | 每机独立进程，天然隔离（无 UI 即无焦点问题） |
| 依赖 GUI | 一定程度上依赖（`BeginExpEx` 在窗体上） | 完全不依赖（走 `SendMethodBytes` + `SysStart`） |

### 2.7 ★ 本路线要回答的三个技术未知

| # | 未知 | 影响 | 验证方式 |
|---|---|---|---|
| U1 | `BeginStartWriteFile` 在**无 MainFrm** 时能否正常落盘（是否内部访问窗体） | 决定产物由谁写 | 宿主 T1 冒烟：只跑 OCP，看文件是否出现且非空 |
| U2 | `ctx.PackReceive` 处理数据时是否**自动**调 `WriteDataNow`，还是要我们显式刷 | 决定是否需要轮询刷盘 | 对比「不刷」与「每点刷」的文件增长率 |
| U3 | `SysStart` 后 `ExpMethodState` 是否会被自己翻回 `SysStop`（前序只能手动置 `SysRuning`） | 决定要不要在采集中维持状态 | 采集窗口内每 2s 打印 `ExpMethodState` |

## 四、风险与回退

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| U1：`BeginStartWriteFile` 依赖窗体 | 中 | 原生 `.cor` 拿不到 | 回退到我们自写 txt（格式已逐字节复刻），`.cor` 交给后续再补 |
| 真机协议与模拟器有差异 | 高（不可避免） | 真机联调才发现 | 本阶段只保证「代码链路正确」；真机差异留成 `docs/99_真机联调清单.md` |
| CS Studio 升级致 API 变 | 低 | 宿主编译失败 | 只依赖 public 未混淆成员（03 §5 已论证），不动乱码字段 |
| 长跑内存增长 | 中 | 多机长跑崩 | `ctx.ReSetData()` / `DataItem.Clear()` 在每实验切换时清；宿主自身只保留窗口 |

**保底方案不变**：`01_寄生式自动化_实施记录` 的 UIA 路线已验证闭环，纯代码路线任何阶段失败都退回它。
